# Teacher SEO and full profile pages

## Scope / flow

Har teacher ke do public pages hain:

1. **SEO overview:** name + all selected subjects + location + unique user ID in the URL.
2. **Full public profile:** name + unique user ID. Clicking the teacher name or **View full profile** on the overview opens this page, including LinkedIn.

No new subject-only, location-only or subject/location listing pages are generated by this feature. Existing city directories remain available.

Pages are rendered by Laravel, without login or JavaScript. No per-teacher HTML files or background generation jobs are needed. Changes in stored profile data are reflected on the next request.

## Creation and updates

`POST /auth/register` and `POST /auth/onboarding/complete` already use `OnboardingController`. Successful teacher registration publishes the two page slugs within the registration transaction, using the selected primary subject and city.

`PUT /profiles/me` supplies up to five `subjectIds` plus profile details. Every teacher profile save checks the saved subjects and location and refreshes the SEO slug when necessary. `PATCH /auth/onboarding` does the same for name/city changes.

Publication requires a completed registration, current teacher account type, non-suspended user, nonblank name/city and at least one subject. Creating an empty teacher record alone does not publish a page.

**Important:** registration currently accepts one primary subject. A teacher who later selects five subjects gets an updated SEO URL containing all five; the earlier URL redirects with HTTP `301`. The full profile URL remains stable after its first publication. Updates to bio, rates or LinkedIn alone do not change URLs. Subject names are ordered alphabetically, then by subject ID; selection order does not create different URLs.

The public read path also requires city and at least one subject. Clearing those, suspending the account, clearing registration completion or changing the account away from teacher makes both pages return `404` and excludes the teacher from the sitemap and city teacher list. Restoring eligibility restores access; this feature does not fabricate a historical unpublish event.

## Cleaner URL routes

Current overview: `/teachers/{seo_slug}`. Full profile: `/teachers/{public_profile_slug}/profile`. This shortens the route prefix while keeping the requested name, all subjects, location and unique ID in the overview slug. The stored slugs and app deep-link identifier are unchanged; only route generation changes. No database migration or bulk rewrite is needed for this route/template update. Existing URL publication/update events keep their original timestamps; this code-level route change does not invent business events.

## URL examples

Example domain: `https://example.com`. IDs below are illustrative user IDs; use the IDs returned by your API.

### One subject at registration

Teacher: Rahul Sharma; subject: Maths; city: Jaipur.

```text
https://example.com/teachers/rahul-sharma-maths-jaipur-42
https://example.com/teachers/rahul-sharma-42/profile
```

### All five subjects and complete supported location

Teacher: Rahul Sharma; subjects: Maths, Physics, Chemistry, English, Hindi; city: Jaipur; state: Rajasthan; country: India.

```text
https://example.com/teachers/rahul-sharma-chemistry-english-hindi-maths-physics-jaipur-rajasthan-india-42
https://example.com/teachers/rahul-sharma-42/profile
```

### Two subjects

Teacher: Anita Verma; subjects: English, Hindi; city: Delhi; state/country omitted.

```text
/teachers/anita-verma-english-hindi-delhi-84
/teachers/anita-verma-84/profile
```

### Same name, subjects and location

Two Rahul Sharma teachers have different user IDs, so URLs do not collide:

```text
/teachers/rahul-sharma-maths-jaipur-42
/teachers/rahul-sharma-maths-jaipur-43
```

### Update, old link and app compatibility

Rahul switches from Maths in Jaipur to Physics in Delhi:

```text
GET /teachers/rahul-sharma-maths-jaipur-42
301 Location: https://example.com/teachers/rahul-sharma-physics-delhi-42

GET /teachers/rahul-sharma-42/profile
200 (current subjects and location)
```

Update state/country along with city when moving; the application uses the provided values rather than inferring them. Name changes refresh the SEO URL on the next supported onboarding/profile save but preserve the stored full profile slug.

The existing `teacher_profiles.slug` remains the app/deep-link identifier. A legacy link such as `/site/teacher/rahul-sharma-jaipur` redirects to the current `/teachers/...` SEO URL once published. Existing `/site/teacher/{seo_slug}` and `/site/teacher-profile/{public_profile_slug}` links also redirect with HTTP `301` to the new routes, even when their stored slug already matches. The redirect goes directly to the current destination. App download links continue passing the legacy slug, not the longer SEO slug. Old SEO URLs resolve through their numeric ID suffix and redirect to the current URL; an alternate prefix with a valid published teacher ID also redirects rather than producing duplicate content. IDs outside the application's numeric range are rejected.

### Location and non-Latin names

Only `city`, `state` and `country` are used. There is no separate locality field in the teacher schema. `addressText`, precise latitude and longitude never enter the URL or public HTML. Malviya Nagar therefore needs a future explicit public-locality feature; do not put a private street address into city.

Names and subject labels are normalized with Laravel `Str::slug`; empty/non-transliterable name slugs use `teacher` for the full profile. The numeric suffix ensures uniqueness. `seo_slug` is a TEXT column so all selected subject names can be retained even when the URL exceeds 255 characters; subject labels are not silently truncated.

## Public page content

| Field | SEO overview | Full public profile |
|---|---|---|
| Approved avatar or initials, name | Yes; name links to full profile | Yes |
| All currently selected subjects | Yes | Yes |
| City, state, country | Yes | Yes |
| Bio | When supplied | When supplied |
| Hourly rate and currency | When supplied; zero displays Free | Same |
| Genuine rating aggregate | When rating count is positive | Same |
| Completed lessons count | Yes | Yes |
| Teaching modes | In person, home tuition, online, when selected | Same |
| Trial | Exact saved trial days, when positive | Same |
| LinkedIn | — | When valid HTTP/HTTPS URL supplied |
| Review comments, rating and date | — | Newest first, 10 per page with previous/next links |
| App download button for messaging | Yes | Yes |

The download button, supporting text and download page invite users to send messages only; they do not advertise booking. This messaging/download copy stays in English across all eight supported language settings: "Download the app to message", "Send messages through the app." and "Get the app to send messages".

LinkedIn opens in a new tab with `noopener noreferrer nofollow ugc`. Existing unsafe URL schemes are hidden and new teacher profile submissions reject them. User text and review comments are HTML-escaped. No unsupported verification badge is shown.

**Not public:** phone, email, raw address, exact coordinates, date of birth, guardian/consent information, passwords, OTPs or credentials. Review author identities are not exposed. Public queries explicitly allowlist columns; adding a new database field does not automatically expose it.

**Current data limits:** teacher qualifications, years of experience, teaching languages, calendar availability, website, YouTube and other social links do not have dedicated teacher profile fields in this project. They are not invented or added as part of this feature. LinkedIn is the supported professional link. Existing bio limits still apply.

The redesigned teacher pages use English labels and messaging-only calls to action, with HTML language `en` and left-to-right direction regardless of language query parameters. Other website pages retain their own language settings.

## API examples

Authenticated teacher profile update (subject IDs must exist):

```http
PUT /profiles/me
Authorization: Bearer <teacher-token>
Content-Type: application/json

{
  "bio": "Patient teacher helping students build confidence.",
  "subjectIds": [1, 2, 3, 4, 5],
  "city": "Jaipur",
  "state": "Rajasthan",
  "country": "India",
  "ratePerHour": 500,
  "currency": "INR",
  "lessonModes": ["online", "home_tuition"],
  "trialDays": 3,
  "linkedinUrl": "https://www.linkedin.com/in/rahul-sharma"
}
```

Assuming IDs 1–5 correspond to the five example subjects, the response is:

```json
{
  "ok": true,
  "teacherSeoUrl": "https://example.com/teachers/rahul-sharma-chemistry-english-hindi-maths-physics-jaipur-rajasthan-india-42",
  "teacherProfileUrl": "https://example.com/teachers/rahul-sharma-42/profile"
}
```

Teacher onboarding responses also include these URL fields when the completed teacher has a listing slug. An incomplete teacher with no slug gets no usable page URL. Existing non-teacher response contracts remain unchanged.

## SEO behavior

Both pages include a subject/location title, contextual description, Open Graph and Twitter share metadata and a canonical link pointing to the full profile. The title uses the first two alphabetically ordered subjects plus name/city to keep it readable; all subjects remain in the overview URL and visible page content. Descriptions use the teacher name, all subjects, public location, teaching modes and available bio, limited to 160 characters. The full profile is the preferred search result; **the long subject/location URL is not a separately targeted canonical search result**. This implements the agreed consolidation of the two overlapping pages and does not guarantee rankings or indexing of the long URL.

Only eligible full profile URLs are listed in `/sitemap.xml`, not both versions. Existing city teacher cards link to the SEO overview. Approved avatars are used in share metadata; unapproved avatars are omitted. Canonical and share URLs omit language, pagination and tracking parameters. Reviews use bounded pagination rather than loading the entire history. Both pages include escaped JSON-LD for Person, WebPage and BreadcrumbList, with actual subjects and valid public links. No fabricated qualifications, review stars or rich-result guarantees are added. Breadcrumbs and the footer link back to the city directory. The responsive layout groups bio, subjects and reviews into separate sections with a visible messaging panel; the panel is sticky on desktop and in normal flow on mobile, so it does not cover profile content.

## Reporting and history

`teacher-profiles` in `config/reports.php` explicitly exposes/searches `seo_slug` and `public_profile_slug` in the existing admin report and streamed CSV export. The shared registry, filter service, CSV exporter, admin session checks and report access logger remain in use.

Admin → Reports → Teacher profiles: each row with a stored SEO or legacy listing slug has an **Open SEO page** button in the first **Details** column. It opens the teacher overview in a new tab. Rows without a listing slug show a dash. Public eligibility rules still apply, so an unavailable teacher page returns `404` even when an admin opens its saved link. CSV exports keep the stored slug values.

Version 1 events:

- `teacher.pages_published`: first persisted publication.
- `teacher.pages_updated`: a subsequent SEO slug change.

The entity ID is the teacher's **user ID**. Snapshots allowlist SEO/full profile slugs, selected subject IDs and city/state/country. Updated events include the previous SEO slug. Publication and events are written inside the same source transaction; a recorder failure rolls back the mutation. These events contain public URL/location information, never raw requests, phone/email, exact addresses, coordinates or credentials. History uses the existing append-only activity contract and is not cascade-deleted with the teacher.

Both page types reuse `page_views.page_type = teacher`, with bounded targets `seo:<user_id>` and `profile:<user_id>`, distinguishing the two without storing a potentially long URL in `target`. Existing `page-views` reports can search by these targets. Legacy page-view rows are unchanged. Redirects are not counted as rendered teacher-page views. Page-view logging remains best effort.

Coverage gaps: no invented publication dates for existing records, no separate history of every bio/rate/LinkedIn edit, subject rename at catalog level, direct SQL/admin mutations or eligibility/suspension transition. No new external event delivery is introduced. Reports show publication/update history separately from current teacher profile state.

## Deployment and verification

The migration adds nullable `seo_slug` and `public_profile_slug` columns. It does not backfill or rewrite existing application records. Deploy the migration with the code using the project's normal deployment process:

```bash
php artisan migrate --force --path=database/migrations/2026_10_27_000038_add_teacher_public_page_slugs.php
```

Do not run application migrations to execute tests. Existing eligible teachers keep their original overview URLs and get a full profile route; their next onboarding/profile save persists the new URLs and publication event. Only future supported saves get a new publication timestamp.

Tests require a **disposable MySQL database ending in `_test`**. The integration suite migrates that database and wraps fixture changes in rolled-back transactions:

```bash
REPORTING_TEST_DATABASE=nearby_teachers_seo_test \
  vendor/bin/phpunit tests/Feature/TeacherPublicPagesTest.php
```

The suite covers selected subjects, both pages, private-field exclusion, legacy redirects, URL refresh, stable full profile URLs, visibility gates, sitemap/city links, safe external links, escaped text, transaction rollback, report filters/CSV/admin access and page-view distinction.
